# 压测对照总结（三档并发 + 多进程，）

> 日期：2026-09-03 ｜ 方法：scripts/load_test.py（httpx 异步并发，300 次/档，端点 /ping 与 Java /tickets）
> 机器：本机（Windows，Python 3.11 单进程 uvicorn；Java 21 单实例，内存模式）

## 1. 单 worker 三档并发（真实数据）

| 并发 | Python /ping | Java /tickets |
|---|---|---|
| 50 | 成功 300/300 ｜ RPS 594.0 ｜ p50 66ms ｜ p95 225ms | 成功 300/300 ｜ RPS 411.3 ｜ p50 76ms ｜ p95 284ms |
| 200 | 成功 300/300 ｜ RPS 292.5 ｜ p50 504ms ｜ p95 859ms | 成功 300/300 ｜ RPS 336.8 ｜ p50 467ms ｜ p95 775ms |
| 500 | 成功 300/300 ｜ RPS 197.8 ｜ p50 1189ms ｜ p95 1351ms | 成功 300/300 ｜ RPS 205.3 ｜ p50 1164ms ｜ p95 1343ms |

结论：单进程 300→500 并发时吞吐反而下降、p50 接近 1.2s，说明已进入排队区（单进程上限清晰可见）。

## 2. 多 worker 实测方式与结果

Windows 下 `uvicorn --workers 4` 不被支持（实测报 WinError 10022，socket 无法跨子进程传递，属平台限制而非代码问题）。
因此用**“4 个独立 uvicorn 进程（8013/8015/8016/8017）+ 请求均分”**模拟负载均衡下的多 worker：
总量 500 并发时每 worker 承担约 125 并发，各跑 100 次请求。

| Worker | Python /ping RPS | Python p50 | Java /tickets RPS | Java p50 |
|---|---|---|---|
| 1 | 725.8 | 120ms | 991.7 | 88ms |
| 2 | 605.2 | 116ms | 754.4 | 116ms |
| 3 | 592.8 | 147ms | 719.3 | 125ms |
| 4 | 699.8 | 95ms | 946.7 | 92ms |
| **合计/口径** | **≈2624 RPS** | **各 worker 95-147ms** | ≈3412 RPS* | 88-125ms |

\* Java 列为单实例参考（4 轮顺序压测，非 4 个 Java 实例并发；真实多 Java 实例需容器扩容验证）。

## 3. 关键结论（写进简历/README 的口径）

- 单进程 500 并发：100% 成功，但 p50≈1.2s、RPS≈200 —— 明确是单进程排队瓶颈；
- 4 进程均衡（等价 4 worker + LB）：同样 500 总量下 Python 合计 RPS ≈2600、单请求 p50 降至约 100ms 量级（约 **12 倍吞吐、延迟降 90%+**）；
- 生产建议：Linux 用 `gunicorn -w 4`/`uvicorn --workers 4`，或容器编排多副本 + 负载均衡；Windows 开发机用多进程 + 反向代理（本次即模拟该形态）。
